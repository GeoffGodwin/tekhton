# m40.2 — State Writer: Milestone ID Field

## Overview

| Item | Detail |
|------|--------|
| **Arc motivation** | Second and final piece of the m40 resume-parity arc. m40.1 added the auto-advance fields; m40.2 fills the more dangerous gap — the bash state writer never emits `milestone_id`. The user-visible symptom on a milestone-mode resume: `_hook_mark_done` skips silently because `MILESTONE_MODE` derived from the rebuilt request is `false`, the manifest never flips, and the operator can run the same milestone successfully several times in a row without it advancing. This was the proximate cause of m34.1 staying `todo` after five successful pipeline runs on 2026-06-02. |
| **Gap** | `internal/proto/state_v1.go::StateSnapshotV1.MilestoneID` already exists. `internal/runner/resume.go::requestFromSnapshot` already reads it: `if snap.MilestoneID != "" { req.Mode = RunModeMilestone; req.Milestone = snap.MilestoneID }`. The break is upstream: `lib/state_helpers.sh::write_pipeline_state` never writes the `milestone_id` JSON key. On every resume, `snap.MilestoneID == ""`, the request falls through to task mode (or stays Resume with empty Milestone), and `env.go:115` derives `MilestoneMode = false`. The finalize chain then runs cleanly but `_hook_mark_done` does nothing because it gates on `MILESTONE_MODE && _CURRENT_MILESTONE`. |
| **m40.2 fills** | One narrow bash writer edit + one Go round-trip test. The writer emits `milestone_id` when `MILESTONE_ID` (or `_CURRENT_MILESTONE`) is in the env at write time. Go side requires no functional change beyond a fixture-driven test asserting the key is read correctly. After this lands, a resumed milestone-mode run produces a proper `[MILESTONE NN ✓]` finalize commit and the manifest flips. |
| **Depends on** | m40.1 |
| **Files changed** | `lib/state_helpers.sh`, `tests/test_state_writer_resume_fields.sh` (extends the m40.1 file), `internal/runner/resume_test.go` (new test case), `VERSION`, `CHANGELOG.md`. |

## Design

### Goal 1 — Emit `milestone_id` from `write_pipeline_state`

Read from `MILESTONE_ID` first (the m26 env contract carrier — see `internal/runner/env.go:164` which emits `MILESTONE_ID="$milestone"` for milestone-mode runs), falling back to `_CURRENT_MILESTONE` for bash-orchestrator paths that haven't migrated to the env builder. Both empty = non-milestone task run = skip the field entirely (omitempty parity with the Go side):

```bash
# Milestone id carry-over (m40.2) — sourced from either the env-contract
# variable populated by the m26 builder, or the legacy bash global set by
# tekhton-legacy.sh. Empty in both means this is a non-milestone task run.
_ms_id="${MILESTONE_ID:-${_CURRENT_MILESTONE:-}}"
if [[ -n "$_ms_id" ]]; then
    printf ',\n  "milestone_id": "%s"' "$_ms_id" >> "$tmp"
fi
unset _ms_id
```

Place this in the same `## Resume hints` section as `auto_advance` (added in m40.1), alphabetically before `notes`. The string must be JSON-escaped — but milestone ids are constrained to `m<NN>(.<dec>)?` so no escaping is actually needed; the cheap printf is sufficient.

### Goal 2 — Tests

- **Extend `tests/test_state_writer_resume_fields.sh`** (the file m40.1 created): add a third test case that drives `write_pipeline_state` with `MILESTONE_ID=m34.2` set and asserts the produced JSON contains `"milestone_id": "m34.2"`. Repeat with `_CURRENT_MILESTONE=m34.2` (no MILESTONE_ID) to prove the legacy fallback works. Repeat with both unset to prove the omit path.
- **Add Go test** in `internal/runner/resume_test.go`: load a fixture envelope with `milestone_id: "m34.2"` and assert `requestFromSnapshot` produces `req.Mode == RunModeMilestone && req.Milestone == "m34.2"`. Add a sibling test confirming the absent-key path falls through to task mode (existing behavior).

### Goal 3 — End-to-end proof

Document the integration path in the milestone close-out notes: a halted milestone-mode run (e.g. produced by setting a SIGINT in the middle of a stage) saves state via `write_pipeline_state`, `tekhton --resume` reads it, the rebuilt request has `Mode == RunModeMilestone && Milestone != ""`, MILESTONE_MODE is `true` through the finalize chain, and `_hook_mark_done` flips the manifest. The recorded fixture in `tests/test_state_writer_resume_fields.sh` is the regression net.

## Watch For

- **`MILESTONE_ID` vs `_CURRENT_MILESTONE` precedence.** The bash side has two carriers for the same intent. `MILESTONE_ID` is the m26 env-contract canonical; `_CURRENT_MILESTONE` is the legacy bash global. Read MILESTONE_ID first; fall back to _CURRENT_MILESTONE; never combine. The two-source precedence is the typical V4-era seam handling and matches what `lib/finalize_commit.sh` does for milestone disposition.
- **No JSON escaping needed for milestone ids.** Ids match `^m[0-9]+(\.[0-9]+)?$` per `manifest.parseEntry`. A naive `printf '%s'` is sufficient. Don't introduce a JSON-escape dependency for this field — it would be over-engineering for a constrained vocabulary.
- **Out of scope:** the `MilestoneDisposition` cache. That's read at finalize time from `_CACHED_DISPOSITION`, not the state file. Resume-restoring it is a separate concern (`COMPLETE_AND_CONTINUE` is the default disposition the Go runner computes anyway, so resume gets correct behavior without persisting it).
- **`requestFromSnapshot` ordering.** Existing code reads `MilestoneID` before `Task`. If both are non-empty (operator-driven hand-edit of the state file), milestone wins. Don't change this — matches the bash legacy behavior.

## Seeds Forward

- **Post-m40**: `tekhton --resume` from any milestone-mode halt produces a proper `[MILESTONE NN ✓]` finalize commit and the manifest correctly advances. The auto-advance loop landed in `cmd/tekhton/run.go::runAutoAdvanceLoop` (b3e05e9) now works correctly through halts because the resumed request carries the auto-advance config AND the milestone id.
- **State writer Go port**: the bash `write_pipeline_state` survives only because the bash orchestrator paths still use it. When the orchestrator ports to Go (post-M39), the writer follows; the fields established here transfer 1:1 to the Go writer.
- **m34.2 onward**: dogfood the m34-m39 stage-port sprint with `--auto-advance --auto-advance-limit N` and trust the resume path. Without m40 this combination silently halts after the first milestone.
