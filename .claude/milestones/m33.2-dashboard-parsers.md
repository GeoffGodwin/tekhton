## Design

### Sequencing note

Lands strictly after m33.1. Cannot start until m33.1's `dashboard.v1` proto structs (`DashboardSecurityV1`, `DashboardReportsV1.Intake`, `DashboardReportsV1.Coder`, etc.) are stable in `internal/proto/dashboard_v1.go` — those are what the StatusReader returns. The m33.1 transition seam (`bashParseSecurity` and friends in `internal/dashboard/emit_*.go`) is the contract this milestone fulfills.

### Goal 1 — `internal/dashboard/parse.go` — StatusReader

```go
package dashboard

// StatusReader is the READ side of the dashboard data layer. It turns
// stage report files (markdown) and metrics records (JSONL, JSON) into
// typed dashboard.v1 payloads.
//
// All methods are read-only on disk and pure on input — they take a path
// and return a typed struct + error. No side effects beyond opening the
// file for read.
type StatusReader struct {
    ProjectDir string
    LogDir     string
}

func NewStatusReader(env *runner.StageEnvV1) *StatusReader {
    return &StatusReader{
        ProjectDir: env.ProjectDir,
        LogDir:     env.LogDir,
    }
}
```

The reader is injected into the Emitter:

```go
// In internal/dashboard/emit.go after m33.2:
type Emitter struct {
    // ... unchanged fields ...
    reader *StatusReader
}

func NewEmitter(env *runner.StageEnvV1) (*Emitter, error) {
    e := &Emitter{ /* ... */ }
    e.reader = NewStatusReader(env)
    return e, nil
}
```

This is the structural change m33.2 makes to m33.1's emitter — wire the reader in, replace the seam calls with `e.reader.Parse<Kind>(...)`, delete the seam helpers.

### Goal 2 — One `parse_<kind>.go` per parser family

| Bash function | Go file | Method signature |
|---------------|---------|------------------|
| `_parse_security_report` | `parse_security.go` | `(r *StatusReader) ParseSecurity(file string) (proto.DashboardSecurityV1, error)` |
| `_parse_intake_report` | `parse_intake.go` | `(r *StatusReader) ParseIntake(file string) (proto.DashboardIntakeReport, error)` |
| `_parse_coder_summary` | `parse_coder.go` | `(r *StatusReader) ParseCoder(file string) (proto.DashboardCoderReport, error)` |
| `_parse_reviewer_report` | `parse_reviewer.go` | `(r *StatusReader) ParseReviewer(file string) (proto.DashboardReviewerReport, error)` |
| `_parse_run_summaries` / `_parse_run_summaries_from_jsonl` / `_parse_run_summaries_from_files` | `parse_runs.go` | `(r *StatusReader) ParseRunSummaries(metricsFile, summariesDir string, depth int) ([]proto.DashboardRunSummary, error)` |

Implementation notes per parser:

**ParseSecurity** (`parse_security.go`):
- Read file line by line. State machine: `outside` → `in_findings` on heading match `^##.*[Ff]indings`.
- For each `^[-*]` line in `in_findings` state, classify severity (CRITICAL / HIGH / MEDIUM / LOW / INFO via case-insensitive substring match) and extract OWASP category via `A\d{2}` regex.
- Mirror bash behavior at `lib/dashboard_parsers.sh:44-89` exactly.

**ParseIntake** (`parse_intake.go`):
- Two-format support: inline (`Verdict: PASS`) and header-then-next-line (`## Verdict\nPASS`).
- Verdict extraction: try inline first via sed-equivalent regex; fall back to header form.
- Confidence: regex out integer.
- Task text: extract `## Tweaked Content` section's first paragraph, collapse to single space, cap at 5 lines.
- Mirror `lib/dashboard_parsers.sh:96-125`.

**ParseCoder** (`parse_coder.go`):
- Status: inline `## Status: VALUE` (most common) or header form.
- File count: count `-` / `*` list items in `## Files Created` and `## Files Modified` sections.
- Mirror `lib/dashboard_parsers.sh:130-149`.

**ParseReviewer** (`parse_reviewer.go`):
- Verdict only: extract value after `^## Verdict` heading.
- Mirror `lib/dashboard_parsers.sh:153-161`.

**ParseRunSummaries** (`parse_runs.go`):
- Primary path: read `metrics.jsonl` line-by-line. Each line is a single JSON object — unmarshal directly into a struct, no string-spelunking.
- Filter rule: skip records where `total_turns == 0` (crash/noise records).
- Derive `run_type` from `milestone_mode` + `task_type` per the bash heuristic.
- Build per-stage `stages` map from individual `<stage>_turns` / `<stage>_duration_s` / `adjusted_<stage>` fields. The bash version has 11 stages enumerated; the Go version reads them from a constant slice (avoid copy-paste drift).
- For records with `total_time_s > 0` but no per-stage duration, distribute proportionally (mirrors the bash estimation logic at `dashboard_parsers_runs.sh:94-100`).
- Fallback path: when `metrics.jsonl` is absent, fall back to reading `RUN_SUMMARY_*.json` files newest-first via `os.ReadDir` + mtime sort.
- Result order: newest-first (the bash version `reverse()`s after collecting).
- Mirror `lib/dashboard_parsers_runs.sh:18-281` (primary path) and `lib/dashboard_parsers_runs_files.sh:14-105` (fallback).

The bash "Python heredoc primary, sed fallback secondary" pattern collapses to one Go path. The fallback was a portability hedge (machines without Python3) that Go obviates. Note the divergent depth-counting semantics the bash sed fallback warned about in its trailing comment (`dashboard_parsers_runs.sh:270-276`) — the Go version uses the Python-path semantics (depth measures pre-filter lines, post-filter records may be fewer). Document the decision in a comment.

### Goal 6 — Parser parity gate

`tests/test_dashboard_parse_parity.sh` runs five scenarios under `internal/dashboard/testdata/parsers/`:

1. **Security report parity.** Fixture: a representative `.tekhton/SECURITY_REPORT.md` with 4 findings (one CRITICAL, one HIGH, one MEDIUM, one LOW). Run both bash `_parse_security_report` and Go `StatusReader.ParseSecurity`; both outputs must produce identical JSON (after key-order normalization — JSON object key order is not guaranteed but the bash builds string-concatenated so the order is deterministic; the Go version uses `json.Marshal` which sorts struct field tags in source-order).
2. **Intake report parity.** Two fixtures (one inline format, one header-then-next-line format). Both must parse identically.
3. **Coder summary parity.** One fixture with `## Files Modified` and `## Files Created` both populated.
4. **Reviewer report parity.** One fixture with a Verdict heading.
5. **Run summaries from metrics.jsonl.** Fixture with 50 records mixing milestone runs, ad-hoc runs, drift runs, and crash records (total_turns=0). Both bash Python-path output and Go output must produce the same 50-record array post-filter (the bash sed fallback path differs in edge cases — gate against the Python primary path).
6. **Run summaries from RUN_SUMMARY_*.json legacy.** Fixture directory with 5 legacy JSON files (no `metrics.jsonl`). Both must produce identical 5-record arrays.

Each scenario uses `jq -S` to sort keys before diff (handles any incidental key-order drift), then `diff -q` for byte comparison.

## Watch For

- **Python heredoc collapse is the highest-leverage simplification.** The bash `_parse_run_summaries_from_jsonl` body has an embedded ~80-line Python script that does the JSON parsing because pure-bash JSON parsing was unreliable. In Go this collapses to a single `json.Unmarshal` against a struct with the right tags. Don't preserve the dual-path (Python primary, sed fallback) — Go's `encoding/json` is the canonical path; the fallback bash sed code was a hedge that Go doesn't need.
- **Depth-counting semantics divergence.** The bash sed fallback path's trailing comment (`dashboard_parsers_runs.sh:270-276`) documents that the bash sed path and bash Python path disagree on what `depth` counts: Python uses `lines[-depth:]` before filtering zero-turn records, sed uses `tail -n $depth` and increments count only for non-zero-turn records. The Go port adopts the **Python semantics** (depth counts pre-filter lines). Document the choice with a code comment citing this milestone and the bash file line.
- **Markdown parsing edge cases.** `_parse_security_report`'s state machine has a subtle "exit findings on another `##` heading that isn't another Findings heading" rule (`dashboard_parsers.sh:58-61`). Preserve it exactly — a report with two Findings sections (e.g. "Resolved Findings" and "New Findings") must aggregate both. The parity gate fixture should include this case.
- **`_parse_intake_report` task text extraction is fragile.** It reads the `## Tweaked Content` section, capped at 5 lines, collapsed to single space. The Go port must preserve all three constraints: section boundary detection, the 5-line cap (`head -5` equivalent), and the whitespace collapse. A regression here changes the `intake.task_text` field in `reports.js` and the static-site Overview pane shows different text.
- **`tekhton-legacy.sh:663` is a stale source line.** That source statement is inside a conditional that may not always run; the file may not be sourced in every code path. Verify after deletion that no code path tries to call a `_parse_*` function — `grep -nE '_parse_(security|intake|coder|reviewer|run_summaries)' .` across the repo (excluding `internal/` and `testdata/`) should return zero.
- **The static-site app.js does NOT change.** `templates/watchtower/app.js` reads `window.TK_*` globals. The parser change is upstream of that — the JSON shape is identical (the parity gate enforces this), so the JS reader continues to work. Don't open `app.js` in this milestone.
- **`lib/metrics_dashboard.sh` is STILL not in scope.** Same Watch For as in m33.1. The bash `--metrics` CLI summary printer (`summarize_metrics`) is a different subsystem; it stays bash until a future milestone bundles it with the `tekhton metrics` Cobra command. Don't touch it.
